## 3. Codex 连续执行协议：消除逐项等待

### 3.1 正常执行循环

每个工作会话按以下顺序运行，不在单个任务结束后询问“是否继续”：

1. 读取短版协议、持久状态和任务图，只加载当前所需规范片段。
2. 核验工作区差异和文件锁；选择依赖已通过、权限允许、资源充足的最高优先级任务。
3. 找到已有实现并复用；补必要测试；实现最小改动。
4. 执行任务级验证。共享合同/账本/适配器变更再跑关键集成和 Crypto 必需回归；前端变更才跑相关前端测试/构建。
5. 保存原始测试输出、退出码、源码/配置/产物哈希和任务证据。没有证据不能 `VERIFIED`。
6. 更新持久状态、任务图、下一动作；有现行版本控制授权时做本地小提交，否则保存审阅补丁，不触发自动 push/deploy。
7. 立即选择下一个可执行任务，直到会话预算结束、全体可执行任务完成，或仅剩真实外部等待/审批。

“每天一个主要目标”改为“每个小任务一个可验证目标”。一天可完成多个彼此衔接的任务，不人为延迟至次日。

### 3.2 必须持久化的最少文件

```text
crypto/plan/hybrid_to_live_tasks.v1_2.json     # 任务图，验收与依赖
crypto/work/hybrid_delivery/state.json       # 运行中的进度和下一任务；新建，不覆盖旧状态
crypto/work/hybrid_delivery/events.jsonl     # 追加式状态/审批/尝试记录
crypto/work/hybrid_delivery/locks/           # 开发/任务/文件所有权，含心跳和失效规则
crypto/outputs/hybrid_delivery/<run_id>/     # 原始证据和阶段报告
crypto/docs/HYBRID_DELIVERY_STATUS.md         # 面向用户的单页最新摘要
```

大型数据和真实秘密不提交 Git。任务图初始所有任务为 `TODO`；截图状态为 `reported_unverified`，不是假装已验证的进度。

### 3.3 任务状态

`TODO → READY → RUNNING → VERIFYING → VERIFIED`。

失败/等待分支：`RETRYABLE_ERROR / BLOCKED_CONTRACT / WAIT_DATA / WAIT_EXTERNAL / WAIT_OWNER / NO_GO / SUPERSEDED`。

- WAIT_DATA必须有缺口、所需数据资格/数量/模式、采集进程、下一检查条件和责任人。
- WAIT_OWNER必须是集中审批表中真正需要用户的内容，不得用于一般编码选择。
- 每个 blocker只阻塞明确依赖它的任务，不能把总项目一键冻结。
- `state.json`是任务调度依据，不是风险授权依据。状态写成PASS不能绕过独立gate验证器。

### 3.4 有界自动修复

- 同一失败最多2次针对性修复；第三次进入根因任务，最多再1次重构修复。
- 同一数据/代码/配置哈希不重复运行昂贵拟合或完整回测，除非预登记数值重复实验。
- 超时、429按官方退避规则与有限重试处理；未知订单状态不属于可直接重试类。
- 连续3轮没有新代码、数据、产物或有效诊断，记录 `NO_PROGRESS`，转做其他任务或等待触发，不驻守空转。
- 测试失败不得删除断言、填假数据或降低业务门槛解决。
- 无信号最多排查预热、缺口、批次同步、状态触发、拒绝分布等已定义原因。确认市场确实无机会后继续观察，不调阈值凑交易。

### 3.5 并行与所有权

最多3个有界角色：集成/状态负责人、数据与验证、数学或执行工程。账本与公共合同始终单一负责人。没有可用多代理能力则串行；不能声称启动了不存在的Agent。

正式数据观察/保护服务必须与训练、编码代理分进程/环境；训练不可耗尽采集器资源。任何生产进程不从编码代理正在修改的工作目录热加载代码。

### 3.6 跨会话自动续跑

优先复用用户已有 Codex 定时任务或受支持运行机制，先核验是否真实存在、是否有权限、工作目录和预算；不要重复创建两小时任务。也可在用户批准的本地调度环境以 `codex exec` 运行固定恢复指令。[S7]

- 开发runner只读取任务状态、调用受限编码会话、保存结果；禁止生产交易凭据和真实交易网络出口。
- 所有调度有单实例锁、最大运行时长、每日预算、退出码、心跳和取消入口。
- 不使用绕过审批/沙箱的选项，也不让runner改自己的安全权限。
- 没有实际调度环境时，如实交付已验证的一次运行/恢复入口。上下文结束时保存状态；下次只需固定“继续执行本计划”，不再编写新计划。
- 会话或电脑关闭并不代表后台仍运行。只有真实存活的服务/调度器日志能支持“持续执行”的说法。[S7–S8]

### 3.7 资源默认值 [N，开发上限，不是新增付费授权]

每次编码会话目标60–90分钟；适配当前平台实际限制。未批准新增云资源/数据/LLM费用时预算为0；既有订阅或已批准额度不由本文件扩张。重训练只在新数据快照或登记的诊断变化时触发；没有新数据不每两小时再训练。

## 4. 门槛与权限：不再用一个 PASS 控制所有阶段

### 4.1 Gate总表

| Gate | 要证明什么 | 通过后可自动做什么 | 不允许什么 |
|---|---|---|---|
| G0 接续可信 | 现有实现、产物、合同与进程对应 | 跳过已完成工作，进入后续任务 | 当截图等同测试日志 |
| G1 开发数据 | 标签可复现、来源/代理/时点正确 | DEV_ONLY拟合 | 宣称未见OOS或交易适用 |
| G2 推断有效 | 实际拟合、诊断、预测检查、支持域合格 | 对匹配目标做受限研究旁路 | 自动通过收益/实盘 |
| G3 报价时序 | 当前数据和标签链真实可用、时钟边界明确 | QUOTE_AWARE观察和合格新标签 | 把接收时间伪作每个价位变更时间 |
| G4 风险数值 | 多币、现有风险线、保护、成本、数值误差 | 风险旁路；符合合同后虚拟缩量 | 虚构精确市场尾部概率 |
| G5 候选集成 | 双通道、writer、账本、恢复、版本一致 | 独立模拟账户研究 | 写原执行准入表 |
| G6 模型验证 | 与执行目标匹配的时间外结果、校准/覆盖和门槛定义 | 登记候选模型和冻结评估 | 自己选最高收益版本上线 |
| G7 收益证据 | 原指标、样本下限、压力和稳定性满足 | 进入实盘审批候选 | 用合成/代理混合样本凑数 |
| G8 执行工程 | Mock、测试网、订单状态、回报、保护、对账可用 | 完成生产适配的技术验收 | 以测试网盈亏证明Alpha |
| G9 发布安全 | 稳定运行、备份/恢复、告警、凭据隔离、账户约束 | 生成READY审批包 | 自行注入实盘交易密钥 |
| G10 用户授权 | 账户、资金、有效期、版本和风险明确批准 | 用户在应用内启用对应实盘方式 | Codex/LLM代下真实订单 |
| G11 小资金复盘 | 实际订单/成交、风险、成本、事故处理完整 | 交付首轮实盘复盘 | 自动放大资金、解除亏损熔断 |

每个gate记录范围、版本哈希、数据资格、证据路径、生成时间、过期规则和阻塞。Data/Model/Performance/Engineering分开。

### 4.2 自动推进条件

前置任务VERIFIED + 必需gate满足 + 权限存在 + 资源预算允许 → 自动推进。样本量不足只阻止相关统计结论；模型不合格仍可开发mock/testnet代码。实盘代码可提前开发，但生产网络和交易能力保持锁定。

### 4.3 不能绕过的总门

```text
READY_FOR_OWNER_LIVE_APPROVAL =
  relevant G2/G3/G4/G5/G6/G7/G8/G9
  AND all frozen policy definitions resolved
  AND no critical open incident

LIVE_ENABLED =
  READY_FOR_OWNER_LIVE_APPROVAL
  AND user-approved exact release/account/risk envelope
  AND user-controlled activation outside the coding agent
```

对仅技术策略、技术+贝叶斯、技术+MC等发布不同gate范围；但本版主验收目标是无LLM的 `T+B+M`，不能因它失败自动换成表现更好的实验臂上线。变更发布目标属于集中方案审批。

## 5. M2收尾：持续可用的数据、时钟与标签

### 5.1 时钟与数据来源

保留已修复的原生事件时间、本机接收时间、独立时钟区段与误差范围。原320秒差异不是简单靠把时间加320秒消除。保存UTC墙钟、单调时钟、服务器校时往返/偏差估计、转换版本；系统时钟跳变开启新区段，不倒写旧证据。

Binance `bookTicker`公开字段没有原生事件时间；`ticker`含E及双边报价/数量、按约每秒更新，但E表示消息事件时间，不证明其每个bid/ask价位刚在E时发生变化。[S1]

因此对当前ticker来源明确 `quote_observation_granularity` 和 `price_change_time_known=false`。可用于与采样粒度一致的观察；不得声称逐笔成交可达性。若策略/保护需要更细粒度，增加有序深度流与快照恢复，不通过扩大freshness容忍度掩盖不足。报价存在不保证给定数量和延迟下完全成交。

生产SIGNED请求必须使用可信时钟和合法recvWindow；不能将扩大recvWindow当成修复错误行情时点。[S2]

### 5.2 两套数据集分开

- `EXPOSED_BAR_DEV`：已有27成熟A标签等，保留原代理执行政策；用于开发、拟合、描述性检查。
- `FORWARD_QUOTE_OBSERVATION`：新发生、真实记录接收和决定时间的报价观察；结果仍是虚拟成交，不等于真实账户成交。
- 无原生价格事件时间的数据另存接收时间研究资格，不混成严格时序数据。
- 未来真实成交单独 `LIVE_EXECUTION`，不得与前两者合并报“我已赚了多少”。

### 5.3 增量管线

复用现有 `hybrid_observation.py / hybrid_clock.py / hybrid_dataset.py / hybrid_features.py / hybrid_labels.py`（准确路径先核验），做到：

```text
闭合bar与完整1H → 规则机会 → 快照冻结 → 延迟政策
→ earliest_fill_at之后的合格报价/代理 → 保护退出
→ 成熟/删失/不可用标签 → 不可变数据快照
```

保留250根连续完整1H、100根完整5m预热，以及每小时12根5m证明，不修改原缺口后重热规则。[P1 §5]

`fill_status`与`label_status`分开；未成交不能填0R、等待自动成熟。已有持仓导致拒绝的技术机会可按冻结的标准单笔参考政策生成counterfactual标签，用于已声明的候选总体研究；不得进入实际虚拟交易数或收益验收。

### 5.4 从“合格报价”到可验收闭环

新增数量漏斗：原始消息、有效消息、有效时间段、闭合批次、预热、技术机会、可尝试、成交、成熟、未成交原因、删失、净新增标签。报告按币种/模式/政策分组。

先做合成完整生命周期测试；再等待真实自然机会验证采集链。同一时点只有单币合格，不等于三币新仓风险评估完整；但不能阻塞其他已有持仓的合法保护。

目标工程观察窗先设连续72小时（新增设计，不替代收益门槛），覆盖实际UTC日界与断连/恢复演练。分母应为预定的交易观察时段，不是收到的消息条数；按预冻结freshness计算可用秒数比例。24小时、72小时报告仅证明对应窗口，无机会要明确原因。

首个真实标签证明接线，不证明收益；等待它时M3/M4/执行工程继续。若72小时无机会，做一次只读漏斗诊断后继续采集，不能强制触发信号。

### 5.5 G3出口

时间源/误差合同明确；重复和乱序可恢复；既有数据不重写；真实自然机会至少一条完整生命周期或明确WAIT_DATA；所有训练标签来源和成熟时点可追溯；质量异常不能生成准入。

## 6. M3：把已拟合模型变成可验证的研究预测器

### 6.1 不重新回到“尚未训练”

复用27条标签的首个拟合产物，核对数据/先验/后验/诊断哈希。27是市场标签数，4×1500是后验抽样数；ESS不是市场样本数。[P1 §6.3]

### 6.2 模型主线与限制

首版保留简单分层Student-t净R回归：模式效应、币种收缩、少量当时可知的特征；不默认启用AR(1)或LLM特征。最多8个是上限而不是必须凑满。开始优先复用已登记的小特征集合。

### 6.3 诊断处理

冻结本轮诊断政策：原则沿用已有已批准值；没有值时在开发阶段登记来源和临时研究配置，不悄悄变成准入批准。官方Stan建议最终推断看R-hat、ESS、发散等多个指标；最大树深度主要是效率警告，需要解释而非直接删掉。[S6]

针对5.68%树深度警告：查看具体参数、链、相关性、数值误差和预测稳定性；优先缩放/重参数化/先验和结构检查。固定模型分布不变的数值修复仍生成新artifact；改变先验/特征/目标则登记模型修订。最多2个登记的修复候选加1次根因处理，不遍历参数寻找最赚钱结果。

必须交付：先验与后验对照、后验预测检查、关键输出数值误差、组覆盖、无法支持的币种/模式、推断失败及弃权原因。

### 6.4 执行目标迁移，不偷换

代理标签模型可以做相同代理目标的开发预测。不能将其直接登记为QUOTE_AWARE净R预测模型。对真实报价目标：采用匹配标签重新拟合/校准或预登记目标迁移验证；证据不足维持旁路。

冷启动不应造成“无模型→无法采集→永远无标签”：不影响原规则的 `T_latency` 观察始终可以生成该执行政策下的候选/单笔标签；训练先做开发检查，再在模型登记完成后的未来时点保存预测。

### 6.5 防止过拟合与重复检验

使用已允许历史扩大开发数据时，按预先固定日期范围和数据授权拉取；仍标已暴露，先看manifest不挑收益窗口。A/B不能因185比27多就直接混合；新标签总体要固定政策、币种/模式、数量参考、成本和依赖组。

最多同时保留1个主模型与1个简单基准、1个登记挑战模型。不在同一评估块不断训练直到通过。新历史/新标签可以形成开发快照，不自动进入冠军。

### 6.6 G2/G6出口分开

G2：推断真实、数值合理、支持域与输出权限明确。可以继续研究旁路。

G6：对冻结目标、时间外数据的概率/区间/收益误差和分组有效性满足预登记标准。缺少门槛先用开发集制定、登记，再冻结未来评估；不能临时看最终结果后定标准。

p_win用事件频率校准；p_edge不拿单笔输赢当“95%胜率”。如果只均值推断适配，就不展示可靠尾部分位数。无证据模型为ABSTAIN，不以0.5或0填充。

## 8. M5：无LLM数学候选集成与持续观察

### 8.1 架构保持两通道、一个writer

  ├─ 高优先级保护：已有持仓/待退出/日界/硬风险

### 8.4 数据观察不是AI驻守

使用可恢复的普通服务完成采集、成熟标签、固定模型预测和日报；无需LLM每秒盯市场。Codex仅在真实任务、代码缺陷、配置待批准或预登记检查节点被唤起。

无信号时保留原因和采集质量；不重复训练、刷测试和产空报告。M5工程通过后可持续积累证据，同时开发M8/M9执行与安全。

## 9. 训练、评估、收益Gate与“等数据”推进规则

### 9.1 三种周期不同

- 开发拟合：标签有效就能做，产物DEV_ONLY；不要求200笔。
- 冻结研究预测：先登记模型、处理和执行政策，再记录未来结果；可在合法研究范围内持续运行。
- 正式绩效评估：训练/校准/评估时间区分，隔离标签重叠、同日跨币依赖；看的是完整资金路径，不只是分类分数。[P1 §9]

### 9.2 第一轮实验锁定

数据准备后登记：允许范围、准确A或B研发参考、主实验臂、开发截止、模型可用时点、未来评估起点、最少样本覆盖、最大观察窗、报告日、试验数量预算、成本和指标哈希。

新增默认观察排期：以首个合法前向评估时点为D0，至少观察28个完整日历日，并在预登记的周末/周度节点检查样本是否满足原下限；最多观察84日后输出本轮明确结论。**这不是28日必能通过，也不是84日后可放宽标准。**该排期在登记前可依据已有有效样本产生速度调整；登记后不得为挑盈利截止日而改变。

日常可以看数据健康和安全；收益模型调整仅用被明确释放的开发数据。若提前查看评估表现并据此更改模型，该块记为已暴露，新模型必须使用新的未见后续块。若在多个周度节点允许正式绩效晋级，需预登记顺序检验/显著性预算；未实现则仅最终预定节点作PASS裁决，其余节点只报样本与描述性结果。

### 9.3 原收益门槛全部保留 [P1 §10.4]

| 条件 | 原值 | 实施要求 |
|---|---|---|
| 净payoff | ≥1.8 | 金额/R口径从原合同核验 |
| BASE PF | ≥1.30 | 原口径一致，另列PF_R/PF_pnl |
| 平均净R | >0 | 信号时冻结BASE分母，完整实际虚拟交易 |
| 固定交易双倍成本PF | ≥1.05 | 不改交易序列，成本不双扣 |
| 完整压力回放净期望 | >0 | 重跑仓位/现金/拒绝路径 |
| 组合最大回撤 | ≤5% | 估值频率、缺价、起止与终止政策固定 |

不把212笔不同实验结果、重叠反事实标签、模型后验样本或5000条模拟路径计入下限。基线失败不代表Hybrid永远不能成功，但必须用相同已登记目标和有效独立证据证明，而非挑窗口。

### 9.4 G7裁决

数据资格、必要样本、各指标、压力、按模式与币种覆盖、去最大赢家/最佳币敏感性和统计不确定性全部有报告；不存在未决核心口径。不给“只看PF>1.3即可”的自动晋级。

若统计门槛未冻结，G7 BLOCKED_CONTRACT；若数据不足，G7 WAIT_DATA；若明确失败，G7 NO_GO。不能因为工程全部完成而人工填PASS。

### 9.5 样本速度与时间估计

每周根据新发生、符合政策的**成熟有效实际虚拟交易**估计最近7/14日速度，分别估计每个模式和有效symbol×mode覆盖缺口：

`预计等待 = max(总样本缺口/总速度，各模式缺口/模式速度，各组缺口/组速度)`。

速度为0时输出无法按当前速度估计；报告依赖和置信限制，不把训练标签数当交易速度。只做排期预测，不改变策略、范围或费用以加速凑数。

1. 锁住失败版本与数据；出明确NO_GO，完成工程交付。
2. 在已授权开发数据检查数据/成本/目标错配或先验主导，最多提出两个有解释的修订实验，不无限模型搜索。
3. 纯bug修复按新版本和新测试推进；策略阈值/目标/资金规则修改进入一次集中方案批准。
4. 新版本不能复用已据此调参的评估块作独立证明。
5. 没有获批修订或新证据时，稳定采集/报告，不无限消耗Codex资源。系统保持SIM_ONLY；这也是合法的交付结论。

## 10. M8：交易适配与订单管理——新增实盘工程，不等模型收益才能开发

### 10.1 第一实施范围

先实现 `MockBroker` 和指定Spot Testnet适配，再做生产只读核对与锁定的交易适配器。复用已验证SDK或清晰的小适配器，不同时支持多家交易所。

实际服务实体、支持币对、账户权限、费用、订单类型从账户与官方API核验。不能把 Binance.com、Binance.US、其他实体和Bybit当同一服务；不能使用VPN等绕过账户或地区限制。

### 10.2 Broker接口（需求，不是已存在命令）

```text
get_capabilities()
get_symbol_rules(symbol)
get_account_snapshot()
get_open_orders(symbol)
get_order(exchange_order_id | client_order_id)
get_fills(cursor)
submit_order(intent)          # 只有测试环境或用户已批准的生产运行时可调用
cancel_order(order_identity)  # 同样受权限约束
subscribe_execution_events()
health()
```

只有执行适配器拥有相应凭据；模型、LLM、Codex和开发runner不读取生产秘密。禁用提现/划转/借贷/杠杆等非本期能力，使用独立账户或可用子账户/隔离额度；如隔离方式不支持则明确限制与审批，不假装存在。

### 10.3 外部交易不是数据库原子事务

新增 `order_intent_id / client_order_id / exchange_order_id / exchange_trade_id`。持久outbox先记录待发送意图；再调用交易所；ack、累计成交、逐笔成交分别处理。

**不能声称网络提交与本地DB形成exactly-once事务。**需要幂等意图、稳定client ID、查询核对和单一writer共同实现可恢复语义。client ID在交易所的唯一范围/可重用规则必须查官方；本地永不把旧经济意图无痕复用。[S2–S4]

```text
CREATED → VALIDATED → RESERVED → SUBMITTING
      → ACKNOWLEDGED / UNKNOWN / REJECTED
      → PARTIALLY_FILLED → FILLED
      → CANCEL_PENDING → CANCELED / FILLED / UNKNOWN
```

`UNKNOWN`不是FAILED：超时或5xx可能已送达撮合；先看用户数据流，再查询订单与成交，必要时停止新仓并告警；**不得盲目重发第二个订单**。[S2]

### 10.4 部分成交、撤单竞态和恢复

- 部分成交立即计入持仓、手续费、剩余预留与保护需求；不等全部成交再保护。
- 撤单请求成功不代表先前没有成交，按最终订单和成交记录核对。
- 消息重复/乱序按订单累计量与唯一成交ID归并，禁止重复扣钱/加仓。
- 主进程重启先核对账户、在途订单与成交游标，再决定能否恢复新入场；不只读本地checkpoint。
- 测试网重置应标新环境epoch，不能把余额消失算成策略亏损。[S5]
- 费用币种、base扣费导致可卖数量减少、dust、分批退出和数量舍入均入账。

### 10.5 精度、过滤和可达性

金额/数量使用Decimal或等价确定精度，不以二进制float直接拼订单。每次启动及规则过期时核验交易状态、tickSize、stepSize、最小/最大数量、MIN_NOTIONAL/NOTIONAL、订单数限制及支持订单类型。[S3]

风险允许的数量向下取整后不满足最小额，则SKIP。**不能自动上调风险、增加资金或换其他币凑单。**报价size不足不能假定整单顶层价成交；小资金也必须记录假设、最大价差、延迟与成交偏差。

原模拟入场政策若与拟生产订单类型不一致，定义新执行版本并重做匹配评估，不能为便于成交直接从限价改市价。

### 10.6 独立保护与资金风险

先做交易所原生保护能力矩阵：可用订单类型、触发价依据、order-list/OCO等能力、部分成交后的可保护数量、数量锁定、取消/替换竞态、网络失败语义。**禁止仅凭API有某个订单名称就认定实盘保护完整。**[S4]

- 首次实盘优先要求交易所端已确认的灾难保护，减少单台机器/网络故障暴露。
- 交易所触发依据可能不同于本地bid策略止损，两者分别标注；触发不保证按止损价成交。
- 同一现货数量被保护单锁定时，策略退出不能另发超量SELL；统一管理持仓数量、保护单与撤换。
- 进入部分成交后保护失败：禁止其他新入场；按用户预批准的撤余单/处理剩余敞口应急政策执行并告警。没有该政策不能进入LIVE。
- 用户手工成交和自动保护不能同时争夺同一仓位。手工模式必须采用明确的单一交易所有者，保护通过用户交易所订单或该模式获批方式设置。

## 11. M9：Mock、测试网、只读账户与发布验收

### 11.1 三层测试，不混用结果

| 层 | 目的 | 收益意义 |
|---|---|---|
| Mock/故障注入 | 重复、超时、竞态、DB失败、保护失败、精度 | 无市场收益证据 |
| Spot Testnet | 请求签名、订单/撤单/回报、环境恢复、权限隔离 | 不证明实盘流动性、成本或Alpha |
| 实盘只读影子 | 核对真实账户、规则、报价与拟下订单；不提交 | 不产生真实成交收益 |

`/api/v3/order/test`只校验订单请求而不进入撮合，不能替代测试网成交生命周期或实盘执行验收。[S4]

测试网真实操作需要用户提供测试网凭据与一次批准；无批准时继续mock与离线实现，不阻塞模型数据线。所有测试凭据与生产凭据隔离、域名明确白名单。

### 11.2 必须演练的故障

提交超时但交易所已接受；ACK丢失；重复成交回报；成交后撤单竞态；部分成交后断网；订单过滤变更；账户余额变化；费用币扣减；深度/报价过期；时钟跳变；用户数据流断连；DB写失败；writer双启动；测试网重置；原生保护失败；手工订单冲突；程序重启；版本不符恢复。

演练必须有输入、期望、实际订单状态、资金恒等式、证据和处理时长。自然市场很难产生的失败用mock注入，不为验收故意在真钱中制造故障。

### 11.3 发布运行环境

在当前稳定本机/已有服务优先完成，不强制迁云、Redis、Postgres、Kubernetes。SQLite可继续用于单writer受控初版，但必须验证真实规模、WAL/备份/恢复与宕机行为；多writer/多用户需求才另做迁移。

运行时与训练/开发分环境，使用不可变release目录、明确入口、依赖锁与启动检查。新release先在影子环境验收，不覆盖持仓中进程代码。正式推送、部署、替换现有服务须有运维范围批准。

### 11.4 运维门槛 [N，冻结后检查]

- 一次连续72小时集成观察，覆盖UTC日界、计划断线恢复和状态复核；不等价于收益样本。
- 初始候选数据SLO建议99%预定观察秒数满足合格报价合同；仅适用于新评估且需独立记录保护可用性。最终值在看验收窗口之前根据策略时效和基础设施能力登记，不能事后改分母。
- 100%实际意图、订单、fill与费用可追溯；重复成交/未知未处理头寸/资金恒等式错误为0容忍。
- 所有关键故障用例通过；有独立健康与保护告警；无未解决critical安全事项。
- 备份恢复从真实文件验证；不只写“有备份脚本”。保留point-in-time manifest，恢复后对账再启动新仓。
- 磁盘、水位、时钟、行情、订单回报、持仓保护、可用资金、日亏损和模型版本均可查。

不得把短信/邮件“接口返回成功”当用户一定收到。上线前做一次实际通知送达确认；无可用告警通道不能无人值守实盘。

### 12.3 资金与密钥安全边界

Codex不创建/调用真钱交易密钥、不代用户下真实单；其shell、模型和定时任务的环境变量中不含生产秘密。用户应用的执行worker由用户部署和授权，只有它的受控身份访问最小权限凭据。默认无提现、划转、借贷或修改风险配置能力；有条件时IP白名单与网络出口限定。[S2]

默认支持 `MANUAL_ASSISTED`：应用输出冻结候选，用户在交易所自行下单、设置保护，系统通过获批只读回报核对。若选择 `APP_SUPERVISED_MICRO`，由用户亲自启动已验收的确定性应用，不是Codex对话代理交易；每次新入场可要求用户在应用内确认，保护退出按已批准政策执行。无人值守自动交易属于额外独立授权和运维要求，不自动包含在本计划的首次上线中。

### 12.4 只在这些情形再中断用户

权限/费用变化；策略/10R/收益合同无法取证且需要裁决；账户限制；重大安全事故；实际资金启用；超出已批准风险/版本/有效期。常规单测、模型诊断、数据等待、工程任务完成不询问用户。

## 13. M11：小资金实盘计划——不把“能下单”当作赚钱能力

### 13.1 原风险上限保留 [P1 §6.6]

单笔预计风险0.25%、组合预计风险0.50%、最多2仓、单币名义25%、日亏损1%、连续3亏暂停2小时。这些是研究既定边界，不代表任何本金规模都适合，也不保证跳空等实际损失不超限。

### 13.2 首轮更保守的提案 [N，必须经A2确认，不自动生效]

| 参数 | 首轮提案 |
|---|---|
| 本金 | 由用户明确提供，不猜测余额，不代充值 |
| 单笔预计风险 | 不超过试点风险基准的0.05%，且不超过批准绝对金额 |
| 总开放预计风险 | 不超过0.10% |
| 同时持仓 | 最多1个 |
| 单币名义金额 | 不超过试点风险基准的5% |
| 当日新增入场 | 最多1次，自然信号不足可0次 |
| 日亏损停新仓线 | 0.25%与批准绝对金额中更严格者 |
| 试点累计损失停新仓线 | 初始试点资金1%与批准绝对金额中更严格者 |
| 自动扩仓 | 禁止 |

比例越保守越可能不满足交易所最小下单額；系统必须跳过，不上调金额来“做一笔测试”。用户可以在审批中选择更低值；任何提高不得突破原上限，也不得由编码代理自己决定。

定义专用试点资金和风险分母：资金流入不自动扩大授权风险基准，出金使可用风险下降；需要改额度时重新批准。累计损失与高水位、日初基准延续既定时序，不能重启后清零。交易以账户实际成交为事实，并包含手续费、价差和其他真实成本；账户外平台/稳定币风险另列，不假装被策略止损覆盖。

### 13.3 启动当天

用户核对所批release、账实相符、无未知订单、行情/时钟健康、保护可用、有效通知、可值守和额度。若没有自然合格信号，不强行下单。首笔发生后核对entry intent、订单、真实fill、费用、保护ACK、退出和账本；生产环境不做故障注入。

### 13.4 试点观察

初始期限14个日历日；每个真实成交后自动核对、每天汇总。首轮至少要求一个完整真实成交生命周期才能声称“已经实盘运行闭环”；少量交易只证明操作可用，不能证明盈利。

到14日没有合格交易，输出 `LIVE_ARMED_NO_ELIGIBLE_TRADE` 并按审批有效期结束；不为完成计划交易。到期仍有持仓按已批准保护/退出政策管理，不直接停止保护。必要延长期或新版本由用户重新批准，不无限续期。

首轮报告包括实际PNL、成本偏差、实际滑点、订单状态差异、保护空窗、漏信号/拒绝、用户执行偏离与风险事件。没有完整fill证据不把截图价格当成交。

### 13.5 上线后修改

生产版本、参数、模型、风险政策冻结。训练工作继续在离线挑战分支，不热替换冠军、不自动放大资金。新模型只有重新走相关Gates和用户发布授权才能替换；已有持仓仍由旧冻结规则管理或按已批准迁移处理。

单笔/短期亏损不自动归因模型失效；真实风险越限或运行异常按事故政策处理。试点盈利也不自动放大资金。

## 14. 故障、暂停、恢复与撤退手册

| 事件 | 自动动作 | 禁止行为 |
|---|---|---|
| 模型超时/版本不符 | 停新仓，保护继续，记录ABSTAIN | 自动改用更乐观模型 |
| 行情缺失/时钟冲突 | 停新仓；有效原生保护保留；无可信报价不伪造成交；告警 | 用旧价显示成功止损 |
| 提交订单超时/5xx | UNKNOWN、查订单/成交、冻结相关新增风险 | 直接重复提交 |
| 部分成交/撤单竞态 | 按实际fill更新、调整保护与预留、核对残量 | 假设全成或全没成 |
| 保护未确认 | 停所有新仓；执行已批准应急策略或通知人工接管 | 继续扩仓赌网络恢复 |
| DB/writer故障 | 停该writer和新仓，保留交易所端保护，恢复后对账 | 两个writer抢写或清库重建 |
| 日亏损/累计损失触线 | 停新仓、取消未成交入场，已有仓位按冻结硬风险政策 | 移动止损、加本金重置亏损 |
| 账户外部手工变化 | 标记差异、冻结新仓、核对后按政策处理 | 默默吸收成模型收益 |
| 凭据泄露/疑似盗用 | 用户撤销/更换密钥，停止受影响worker，核对账户 | 继续在日志输出密钥 |
| 测试网reset | 环境epoch切换，封存旧test账本重新初始化 | 计入真实损失或PAPER收益 |
| 升级失败 | 回退代码及兼容读状态，恢复交易前核对真实账户 | 回滚数据库抹掉已经成交订单 |
| 实盘授权过期 | 不再入场，持续既有保护/按政策退出，通知用户 | 自动续期、清空已有仓位记录 |

新仓暂停、取消入场、保护保留、应急清仓四个动作分开命名。`stop`不能默认撤掉所有保护订单。应急出售/全平只由用户明确批准的应用策略或用户亲自执行；编码代理不得代操作。

## 17. 启动、恢复、暂停和验收命令的交付要求

### 17.1 先复用，再实现统一入口

让Codex探测已有CLI/脚本；有合适能力直接包装。不先创造十个空文件。最低统一能力：

`status / next / run-ready / verify / resume / pause-development / evidence-report / prepare-live-approval`。

这些都是**待实现能力**。本包只提供文档、任务数据和包完整性验证脚本，不声称上述命令现在能运行。

运行手册最终给出实际工作目录、解释器、已验证命令、退出码、服务身份、停止/恢复方式。`run-ready`只允许开发和研究任务，绝不包含“替用户下真实单”。

### 17.2 一次性启动语义

用户将本包导入项目并发送固定启动文案，即要求Codex：先增量确认、创建状态、接着连续执行所有可执行开发任务，直到工程交付和实盘审批准备；不再逐步请求下一份计划。外部批准未到时继续其他分支。

已有平台沙箱、审批和联网限制必须遵守。未拥有调度能力不能伪称会在后台继续；保存恢复点，不需要重新设计计划。

### 17.3 恢复语义

无论换模型、换对话或上下文压缩，读取同一短协议+状态+当前任务证据继续。不要信任聊天中的“都做完了”，也不要因为新会话就全项目重审。

正在运行任务先看PID/锁/心跳，禁止重复启动。锁过期只回收开发任务锁，不抢原采集或生产writer。中断任务重入前核验产物和外部状态。

### 17.4 最终完成条件

工程部分：数据/模型/风险/模拟/订单适配/测试网/保护/对账/恢复/报告都有实际证据；文档链接与产物可解析；没有未标记的权限或政策缺口。

资金部分：只有用户明确启用后的账户成交事实，才可以进入LIVE状态；未经批准就停在READY。首次实盘结果完整归档，即使亏损，也不删记录或改模型掩盖。

如果永远没有足够Alpha证据，最终状态为 `ENGINEERING_COMPLETE_RESEARCH_NO_GO`，系统交付但不交易。无需继续向ChatGPT询问下一步，本计划已包含继续研究/等待/撤退分支。

## 18. 需求追踪、质量检查与本版不承诺的事情

### 18.1 必须可测试的不变量

1. 已完成任务自动进入下一READY任务，不等“继续”指令。
2. WAIT_DATA只阻塞有关数据结论，mock、拟合检查和安全工程继续。
3. G1允许开发拟合；G2/G6/G7/G10互不等同，27标签与6000后验样本分开。
4. 时钟/报价冲突不通过扩大容忍度、改写历史或伪造E修复。
5. 保护通道独立；交易所保护不是止损价成交保证。
6. 经济机会/评估/意图/订单/成交身份分开；UNKNOWN订单不得盲目重下。
7. 部分成交立刻计入真实敞口、费用和保护；撤单与fill竞态可恢复。
8. 模拟价、报价观察、测试网、真实成交严格隔离。
9. 已暴露历史不重命名独立OOS；正式评估不偷看改模，不凑独立样本。
10. 日亏损/累计损失/原10R不被重新解释成更易通过的条件。
11. 风险数量不足最小额就SKIP，不自动上调资金。
12. Codex不能读生产secret、写受保护批准或调用真实订单接口。
13. 用户审批绑定账户/版本/额度/期限，撤销或过期停新仓并保留保护。
14. 回滚不抹去真实fill，恢复先对账再准入。
15. 训练/代码自主推进不等于自动真钱交易；不使用绕过沙箱的运行选项。
16. 所有UNKNOWN/FAIL/WAIT有证据和下一动作，不能一键伪造PASS。

本包已经提供：完整规划、连续执行协议、任务依赖、gate/审批模板、启动/恢复文案、原V1.1副本及包内一致性检查。
